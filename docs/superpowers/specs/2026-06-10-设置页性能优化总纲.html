设置页性能优化总纲

类型：spec（规格）  |  日期：2026-06-10  |  状态：active  |  置信度：high
取代文档： 第一性原理分析 · 量化系统设计
速答：设置页卡顿的根因不是"缺 FBO"或"缺预热"，而是每一帧做了不该做的工作：不可见 section 的 widget 仍然执行、静态文本每帧重建、后台 job 结果集中合并且与交互帧重叠。

当前代码状态：FBO 正在从项目中删除（约 60% 完成）；CSectionLoader 四状态机推进全部 section；资源 Jobs 的 IDLE_DRAIN 后台预算过大（24）导致 backlog 膨胀。

最新数据（2026-06-09）： FAIL p99 = 25.547ms · spike = 552 · 第一热点 settings:tee Work Drain 5575ms（单帧合并 493 个 job）

核心目标：设置页任意交互帧时间 ≤ 8.33ms（120Hz），最差帧 p99 ≤ 16.67ms（60Hz）。

1. 问题定义

1.1 用户感知到的问题

玩家在游戏中打开设置页、切换 tab、滚动皮肤列表时，画面会明显卡一下甚至卡住几秒。这不是"画面不流畅"，而是帧时间尖峰——某一帧突然耗时几十甚至几百毫秒，超过了显示器刷新周期。

  • 打开设置页：按 Escape → 设置，画面停顿 100-500ms 才出现界面
  • 切 tab：从 General 切到 Tee，画面停顿 50-200ms
  • 滚动皮肤列表：滚动不跟手，偶尔卡一下
  • 静止不动：什么都不做时帧时间 2-3ms，很流畅

1.2 为什么会卡 — 帧预算

DDNet 每一帧要做两件事：游戏渲染（世界、实体、特效、HUD）和菜单渲染（设置页、服务器列表）。这两件事跑在同一个线程里，共享同一帧的时间预算。

一帧 16.67ms（60Hz）
├── 游戏渲染：8-12ms
├── 菜单渲染：2-4ms（正常）
└── 剩余：给下一帧

当菜单渲染突然从 2ms 涨到 200ms，这一帧就"爆了"——游戏画面停顿，玩家感受到卡顿。优化的目标不是让菜单渲染"更快"，而是让它不要突然变慢——消灭尖峰帧。

1.3 范围边界

本轮只做设置页：

  • 设置页全部 tab：General、Tee、Appearance、Controls、Graphics、Sound、Assets、DDNet、TClient、QmClient
  • Tee 页的皮肤列表加载与滚动
  • 性能量化系统（采集 + 分析 + 报表）

明确不做（延后到有证据时再考虑）：

  • Server Browser 的列表交互优化（不同根因——同步遍历 vs 资源合并）
  • Demo Browser 的目录扫描异步化
  • Assets / Workshop 的进一步优化
  • 全局 scheduler 大重构

2. 量化目标

2.1 帧时间分层目标

指标目标值理由
UI 帧时间均值≤ 4ms为游戏渲染留足 12ms+ 预算（60fps）
交互帧（切 tab/滚动）≤ 8ms不超过 120Hz 刷新周期
最差帧 (p99)≤ 16ms不超过 60Hz 刷新周期；超出即用户可感知卡顿
首帧（冷启动进入设置页）≤ 33ms允许一次较长帧，但不能连续两帧超标
关键洞察：帧时间的 p99 比平均值重要得多。一次 50ms 的卡顿远比 10 次 5ms 的微波动更影响体验。优化应优先消灭"尖峰帧"。

2.2 无上限 FPS 指标

无上限 FPS 是设置页性能最直观的端到端指标。它不解释瓶颈来自哪里，但它直接回答"用户最终感受到的吞吐量有没有变好"。

指标用途解读
avg FPS观察整体吞吐量同路径优化后 avg 上升，通常说明总 CPU/GPU 成本下降
min FPS捕捉最差体感和尖峰min 下降或长期偏低，优先回查 p99、长帧 timeline
max FPS观察稳态上限只作辅助，易受计数窗口、后台负载、驱动限帧影响

2.3 量化验收标准

验收项指标测量方式
打开设置页首次渲染≤ 1 帧 > 33ms, 后续帧 ≤ 16msqm_perf_debug
切 tab（如 General → Tee）≤ 8msqm_perf_debug

3. 实际代码现状

本章描述的是代码仓库中的实际实现，不是设计意图。所有结论基于当前分支 codex/axiom-script-governance 的代码。

3.1 设置页渲染路径

设置页每一帧的调用链：

CMenus::Render()                          # menus.cpp:2341
  └─ RenderSettings(MainView)             # menus_settings.cpp:4352
       ├─ 绘制左侧标签栏（10 个 tab）
       ├─ 检测当前选中的 tab
       └─ 对选中 tab 的内容区域：
            ├─ [FBO 缓存 — 正在删除] DrawSettingsPageRuntimeCache()
            ├─ [FBO 预热 — 正在删除] PrewarmSettingsSectionRuntimeCache()
            └─ [实际渲染] RenderSettingsXxx(ContentView)
                 ├─ CScrollRegion::Begin/AddRect/End    # 滚动区域
                 ├─ CUi::DoButton_Menu/DoLabel/DoEditBox # CUI widget
                 └─ ui_widget::DrawCard/PrimaryButton    # QmUI widget

核心调度器：CSectionLoader

src/game/client/components/section_loader.cpp

CSectionLoader 用一个四状态机管理每个 section 的生命周期：

状态动作说明
UNINITIALIZED调用 MeasureFn 测量高度 → MEASURING每个 section 的起始状态
MEASURING计算视口优先级；靠近视口则渲染紧凑版 → COMPACT预取边距 200px
COMPACT如果有预算（每帧 5ms，最多解锁 2 个）且优先级高 → FULL预算用完后保持在 COMPACT
FULL如果脏了则重新测量，调用 RenderFullFn 完整渲染真正的"用户看到的渲染"

关键问题：所有 section 不管在不在视口内，都会经历 UNINITIALIZED → MEASURING → COMPACT 的推进。视口外的 section 至少会被测量高度和渲染紧凑版。

预热函数 Warmup() 走的是 RenderCompactFn（轻量路径），但首帧展示用的是 RenderFullFn（完整路径）——预热做了工作，首帧还是冷的。

3.2 FBO：正在从项目中删除

FBO（Frame Buffer Object）曾被用来做 section 的静态层缓存：把 section 的不变部分预先渲染到纹理，后续帧直接贴纹理。但 FBO 创建+录制+blit 成本（1-3ms）常高于实时渲染（0.3-0.5ms），且已出现用户可见 bug。

当前状态：FBO 删除约 60% 完成。10 个文件已修改（section_loader、settings_runtime_cache、settings_warmup、menus.h/cpp 等），剩余 4 个文件的调用点待更新。代码当前处于编译不通的中间态。

已完成删除：

  • section_loader.h/cpp：FBO 渲染目标、缓存有效性、静态/交互层拆分全部剥离
  • settings_runtime_cache.h/cpp：FBO 枚举值、渲染目标注册表、预热计划全部移除
  • menus.h：所有 FBO 缓存数组和函数声明移除
  • menus.cpp：DestroySettingsPageRuntimeCaches 等 FBO 函数实现移除
  • settings_warmup_test.cpp：约 20 个 FBO 测试用例移除，新增 3 个"源码不再引用 FBO"的合约测试

待完成（调用点未更新）：

  • menus.cpp：InvalidateSettingsRuntimeCaches 仍调用已删除的 FBO 函数
  • menus_settings.cpp：10+ 处 DrawSettingsPageRuntimeCache 调用仍存在
  • menus_tclient.cpp：4 处 FBO 相关调用仍存在
  • config_variables_qmclient.h：qm_settings_fbo_cache 配置变量仍存在

文档立场：FBO 删除是本仓库的既定方向。后续优化不依赖任何 FBO 路径。

3.3 资源 Jobs 系统

src/game/client/components/settings_resource_jobs.h / .cpp

核心是一个 PID 风格的吞吐量控制器，根据当前帧的状态自动调整预算。

四种运行模式：

模式触发条件后台请求预算说明
SCROLL_ACTIVE用户正在滚动0交互优先，不发后台请求
POST_SCROLL_RECOVERY刚停止滚动0恢复期，仍不发后台请求
IDLE_VISIBLE空闲但可见区未稳定可变温和推进
IDLE_DRAIN空闲且可见区已稳定24（问题）全速推进后台队列

问题就在 IDLE_DRAIN 的预算 24：当用户切到 Tee 页并静止不动时，每帧允许最多 24 个后台请求。对于 1000+ 皮肤的列表，这会迅速积累数百个 BACKGROUND_REQUESTED 的皮肤。当这些皮肤陆续完成 decode 后，主线程在某一帧集中合并——perf 数据显示单帧合并了 493 个 job 结果，耗时 5575ms。

当前逻辑在"健康进展"（有加载完成）时不会限制新的后台请求——只要还有东西在加载，就可以继续往队列里塞。这导致了 backlog 的无限膨胀。

3.4 皮肤加载链路

src/game/client/components/skins.h / skins.cpp

每个皮肤有 7 个状态：

UNLOADED → BACKGROUND_REQUESTED → PENDING → LOADING → LOADED
                                               → ERROR
                                               → NOT_FOUND

三层优先级加载：

  1. 可见区（VISIBLE）：立即升级到 PENDING，不受延迟限制
  2. 预取区（PREFETCH）：等待 100ms 后才能进入 PENDING（防快速滚动抖动）
  3. 后台（BACKGROUND）：由吞吐量控制器的背景请求预算控制

3.5 预热系统

src/game/client/components/settings_warmup.h / .cpp

CSettingsWarmupScheduler 在客户端启动时运行，预热走的是 RenderCompactFn（轻量路径），目的是填充字形图集和预热纹理——但它不走 RenderFullFn（完整路径），所以首帧展示时仍然需要创建文本容器。预热系统本身工作正常，问题在于预热内容与首帧实际需求不匹配。

4. 第一性原理：UI 性能优化的本质

4.1 一帧里到底发生了什么

Frame Time = CPU 提交 + GPU 绘制 + 同步等待
           = (布局计算 + 文本创建 + 输入检测 + 状态更新 + Draw Call 提交)
           + (顶点处理 + 光栅化 + 像素着色 + 混合)
           + (SwapBuffers / v-sync + 驱动同步)

优化每一帧本质上就是减少上述每一项的工作量，且只在变化时才做。

DDNet 的特性决定了很多"通用优化手段"不适用：2D 俯视角游戏，没有后处理链（bloom、motion blur、SSAO），UI 和游戏渲染共享同一个 GL/Vulkan context，菜单渲染不是独立线程。

4.2 六个优化维度（按影响力排序）

维度 1：少做 — 只处理可见和变化的部分

原则：不可见的 UI 元素不应消耗 CPU/GPU 时间。

反模式：每帧遍历所有 section/行/项，即使 90% 在屏幕外。

DDNet 现状：CSectionLoader 虽有视口优先级，但 MEASURING 阶段仍会测量所有 section 高度。

对应策略：B（视口外 section 跳过 widget）、C（列表虚拟化）

维度 2：少提交 — 减少 Draw Call 和状态切换

原则：每个 Draw Call 都有 CPU 驱动开销。合并提交减少开销。

反模式：每个 UI 元素单独触发一次绘制。

DDNet 现状：CUI 直接调 Graphics()->QuadsDrawTL()，没有统一的批处理层。

对应策略：E（Section 内 Quad 批处理）

维度 3：少画 — 减少 Overdraw 和像素填充

原则：每个像素被多次绘制浪费 GPU 填充率。

DDNet 现状：QmUI DrawCard() 渲染 4 层。但 DDNet 2D 游戏的桌面 GPU fill-rate 充足，overdraw 通常不是主瓶颈。

对应策略：P2 优先级

维度 4：少重建 — 缓存静态内容

原则：静态文本、布局每帧重建白白消耗 CPU。

反模式：每帧重新创建文本容器。

DDNet 现状：CUIElement 提供缓存但覆盖率不足。很多地方仍用不缓存的 DoLabel。

对应策略：A（文本缓存全覆盖）、F（布局脏检测）

维度 5：少等待 — 异步化重活

原则：I/O、解码、GPU 上传不应阻塞主线程，尤其不应阻塞交互帧。

反模式：用户滚动时主线程集中合并 493 个 job 结果。

DDNet 现状：资源 Jobs 已有异步框架，但 IDLE_DRAIN 后台预算过大，合并阶段无严格帧预算限制。

对应策略：D（Job 合并帧预算限制）

维度 6：少分配 — 避免每帧内存分配

原则：malloc/free 在游戏循环中导致不可预测的尖峰。

DDNet 现状：ImGui 式 callback lambda 可能触发分配。这个维度的收益通常较小（几微秒级）。

对应策略：P3 优先级

4.3 优化决策树

面对任何 UI 性能问题，按此顺序判断——这个顺序本身就是按"投入产出比"排的：

1. 能不做吗？        → 裁剪、虚拟化、跳过不可见区域（收益最大）
2. 能少做吗？        → 脏检测、缓存、只更新变化部分
3. 能做更快吗？      → 批处理、减少状态切换
4. 能异步做吗？      → 后台线程/Jobs 池、延迟提交
5. 能不分配吗？      → 对象池、预分配、零分配热路径

5.3 哪些是根因，哪些是表象

根因（优化这些能从根本上减少工作）：

  1. 视口外 section 仍在执行 widget（维度 1：做了不该做的事）
  2. 文本容器每帧重建（维度 4：没缓存该缓的）
  3. IDLE_DRAIN 后台预算过大 + backlog 无上限（维度 5：异步完成 ≠ 主线程不爆）

表象（只掩盖问题）：

  1. FBO cache miss（真正的问题是为什么要重建，而不是为什么没缓存）
  2. p99 高（真正的问题是尖峰帧是从哪来的）
  3. 预热"未命中"（真正的问题是预热路径和渲染路径不一致）

6. 优化策略

策略 A：文本缓存全覆盖 P0 低风险

对应维度 4（少重建）

现状：CUIElement 已内置 text container 缓存，但设置页大量 DoLabel 调用走不缓存的版本，每帧创建临时 text container。

改法：将静态文本改为 SettingsTextElement() 或本地 CUIElement 缓存版本。

// 改前（每帧重建 text container）：
Ui()->DoLabel(&LabelRect, aLabelText, 10.0f, TEXTALIGN_ML);

// 改后（复用，只在文本变化时重建）：
CUIElement &El = SettingsTextElement(SETTINGS_TCLIENT, TAB_GENERAL, "my_label");
Ui()->DoLabel(El.Rect(0), &LabelRect, aLabelText, 10.0f, TEXTALIGN_ML);

量化字段：text_new=N text_reused=N

预期收益：每 section 0.5-2ms。改动量小（~50 行/页面）。

策略 B：视口外 section 跳过 widget P0 中风险

对应维度 1（少做）

现状：CScrollRegion 只做 GPU 端裁剪（scissor），CPU 端仍走完所有 widget 函数。

改法：section 级增加可见性判断，完全在视口外时只保留高度，跳过所有 widget。

if(!SectionRect.IsIntersecting(ViewportRect, PrefetchMargin))
{
    pSection->SkipRenderHeight = pSection->CachedHeight;
    return; // 不调任何 widget
}

量化字段：sections=N sections_visible=N

预期收益：视口外 section 节省 80%+ CPU。多 section 页节省 5-15ms。

策略 C：列表虚拟化 P1 中风险

对应维度 1（少做）

现状：皮肤列表遍历全部项，即使只有 8-16 行可见。

改法：只遍历和渲染可见行 + 1-2 行预取缓冲。

量化字段：rows_total=N rows_visible=N rows_rendered=N rows_skipped=N

预期收益：含 100+ 项列表节省 8-20ms。

策略 D：Job 合并帧预算限制 P0 中风险

对应维度 5（少等待）

现状：IDLE_DRAIN 后台预算 24，"健康进展"时允许继续扩大 backlog。导致 493 个 job 在同一帧合并。

改法：

  1. IDLE_DRAIN 后台请求预算 24 → 8
  2. 增加硬 backlog 上限：HardBacklogLimit = max(CountFuseLimit, DefaultBudget * 8)
  3. 收紧"健康进展"条件：loaded 和 admitted 的 delta 都 ≤ 0 才允许扩大

量化字段：event=work_drain stop reason

预期收益：消除 5575ms 级别的尖峰帧。

策略 E：Section 内 Quad 批处理 P2 中风险

对应维度 2（少提交）

现状：每个 widget 独立提交 draw call。一个 section 10 个 button = 20 draw calls。

改法：收集 section 内同材质 quad → 一次性提交。不改变 CUI immediate-mode 语义。

量化字段：draw_calls=N

预期收益：每 section 0.3-1ms。

策略 F：布局脏检测 P1 中风险

对应维度 4（少重建）

现状：section 高度、列宽等布局输入每帧重算。累积到几十个 section 时不可忽略。

改法：缓存 section 高度、行高、列宽。dirty key：viewport 宽高、UI scale、语言、字体大小、配置展开状态。

量化字段：layout_dirty=0/1 dirty_reason=...

7. 量化系统设计

本章描述量化系统的设计意图，不是进度报告。已实现的标 ✅，待实现的是设计目标。

7.1 设计目标

量化系统回答三个问题：哪里慢？（归因到 stage）→ 有多慢？（百分位 + 尖峰检测）→ 比以前好还是差？（同路径对比）。两个层次的指标不能互相替代：内部 perf/* 字段归因，无上限 FPS 做体感验收。

7.2 采集层（C++ 侧）

阈值

当前客户端使用 1ms 作为默认采样阈值。开发/自测用 1ms（捕获所有超出 UI 预算的帧），用户反馈收集用 4ms（平衡信息量和日志量）。

结构化字段（设计目标）

# 页面切换
event=page_switch page=... from=... to=... dur_ms=...

# 列表帧
event=list_frame page=... items_total=... rows_visible=... rows_rendered=... rows_iterated=... rows_skipped=...

# Section 渲染
event=section page=... section=... dur_ms=... visible=0/1 dirty=... text_new=... text_reused=...

# 工作排空
event=work_drain page=... kind=merge/finalize/upload/publish count=... bytes=... dur_ms=... stop=...

# FPS 摘要（操作结束后输出一次，不是每帧事件）
event=fps_summary operation=... page=... fps_avg=... fps_max=... fps_min=... cap_limited=0/1

# QmUI 独立归因
event=ui_runtime page=... nodes=... layout_ms=... layout_dirty=0/1 anim_ms=... render_bridge_ms=... draw_calls=...

7.4 报表层（ECharts HTML）✅ 已实现

自包含 HTML 报表，浏览器直接打开。特点：

  • 莫兰迪色系（低饱和度、论文式排版）
  • 对数 Y 轴：正常帧 1-4ms 和尖峰帧 100ms+ 在同一张图里都清晰可见
  • 三条帧预算标线：4.17ms (240Hz, 紫色) / 8.33ms (120Hz, 青色) / 16.67ms (60Hz, 玫红)
  • dataZoom：时间轴可拖拽缩放
  • 采样偏差自动检测：p5 > 4.17ms 时自动警告
  • Session 自动对比：自动找上一次日志，逐指标计算 delta

关键设计决策：

  • 为什么不用 Python？ TS + tsx 只需 npm install，DDNet 已大量使用 JS/TS 生态
  • 为什么 ECharts？ dataZoom 对时间序列体验极佳，内置 boxplot
  • 为什么 HTML 而不是 PNG？ 可交互（缩放、tooltip），无需 headless 浏览器
  • 为什么 Timeline 用对数 Y 轴？ 极端离群值（1ms vs 5575ms），线性轴下尖峰撑满高度、基线不可读

8. 实施路线

8.1 Phase 0：实现前 UI Bug Audit

在动任何性能代码之前，先确认要改的路径上没有已知 bug：列出所有受影响的页面和操作路径 → 搜索已有 bug 报告 → 复查上轮优化副作用。

8.2 Phase 1：源头降温

P0（最高优先）：

任务策略目标瓶颈预期收益
补全所有 section 的静态文本缓存AB4每 section 0.5-2ms
Section 测量延迟化 + 视口外跳过 widgetBB2, B3多 section 页 5-15ms
IDLE_DRAIN 预算 24→8 + 硬 backlog 上限DB5消除 5575ms 尖峰

P1（高优先）：

任务策略预期收益
皮肤列表虚拟化：只遍历可见行C100+ 项列表 8-20ms
布局脏检测 + 缓存 section 高度F多 section 页收益明显
QmUI runtime telemetry 分离—避免 CUI/QmUI 混归因

P2（中优先）：

任务策略预期收益
Section 内 Quad 批处理E每 section 0.3-1ms
减少非交互元素的 DoButtonLogic—每 section 0.1-0.3ms

8.3 Phase 2：缓存

只在源头降温做完、且 telemetry 证明某个 section 实时渲染成本仍 > 0.5ms 时才考虑按需启用缓存。对于 DDNet 2D UI，缓存的 blit 成本（1-3ms）常高于实时渲染（0.3-0.5ms）。

8.4 Phase 3：锦上添花

  • UI 图标合并纹理图集
  • Overdraw 量化分析
  • 每帧内存分配审计

8.5 明确不做

  • ❌ FBO 扩展/保留：FBO 正在从项目中删除
  • ❌ 全局 Draw List 批处理：与 upstream 架构冲突
  • ❌ 引入 retained-mode UI 框架
  • ❌ Server Browser / Demo Browser 优化：等设置页做完再说
  • ❌ 全局 scheduler 大重构
